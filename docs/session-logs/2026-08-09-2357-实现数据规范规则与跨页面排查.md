## 按新规则执行的同类问题排查与修复

经验来源：会话日志 `2026-08-09-2326`（空字符串数字字段导致 Form 反序列化失败）

排查结果：
- **伏笔回收章节（expected/actual_payoff）**：前端会把 `null` 转成字符串 `"null"` 传给后端 `Option<i64>` → 400，且无法清空字段 → **已修复**
- 事件 `chapter_id`、角色 `age`、脉络 `chapter_start/end`：同为数值字段，存在同类风险 → **已修复**
- 其他字符串字段无此风险；项目创建/角色新增等查询参数不受影响

修复方式：
- 新增 `commands/params.rs`：`parse_optional_i64`（空 = 不修改）、`parse_clearable_i64`（空 = 清空，三态 Keep/Clear/Set）
- 后端数值字段统一改为 `Option<String>` 宽松接收，清空语义明确
- 前端 `updateForeshadow` 对 null 回收章节传空字符串（清空），不再传 `"null"`
- 新增两个回归测试：伏笔清空回收章节、事件空章节号保留原值

## 沉淀

- 可复用模式：所有 Form 数值字段统一走 `commands/params.rs` 宽松解析；清空语义用三态类型表达
- 后续新表单接口必须引用本规则与 params.rs，禁止再次直接声明 `Option<u32>` 等强类型接收表单空值
