# 修复「档案事实提取失败」并优化 萌芽-大纲-细纲-笔耕 工业化流水线

## 任务目标

1. 排查笔耕保存后红字「已保存（档案事实提取失败，可在图谱中手动维护）」的根因并修复。
2. 优化「萌芽 → 大纲 → 细纲 → 笔耕」的创作流水线，让长篇产出更接近工业化、可验收、可回溯。

## 根因定位（已实证）

对 `project-msm1wauz10dovf` 第 1 章实际调用提取接口后，发现不是“模型没配好”，而是两个叠加问题：

1. **JSON 形状不匹配**：提示词要求输出 `{"facts":[...]}`，但后端按 `Vec<ExtractedFact>` 解析；模型按要求返回对象时必然解析失败。
2. **思考型模型截断 JSON**：extractor 绑定 kimi-k3，配置 `thinking_mode=Always`。实测网关把 `reasoning_tokens` 计入 `completion_tokens`；旧代码只给 `max_tokens=3000`，思考一长就截断在 JSON 闭括号前，表现为“LLM 输出不是合法 JSON”。修复后再次实测，提取成功并落档案。

## 关键决策与取舍

- **事实提取解析改为宽容归一化**：先走统一 `parse_llm_json`，再同时接受 `{"facts":[...]}` 与裸数组 `[...]`；解析失败仍显式报错，绝不静默当“本章无事实”。
- **新增 `structured_output_tokens`**：所有 `json_mode=true` 的调用至少 4096 tokens，长文本输出（细纲/改写/级联改写/萌芽提案）至少 8192，并 clamp 到模型自身 `max_output_tokens`。防止同一截断问题在审校、改写、级联、细纲、萌芽等模块复发。
- **提取器现在能看到与本章相关的档案清单**：系统提示词注入正文中实际提到的 characters/organizations/settings/foreshadows 名单（避免全本名单膨胀），模型只会对已建档角色用 `character_update`；未建档主角强制 `new_character`，避免主角漏档。
- **未建档角色收到 `character_update` 时自动补建**：不静默丢事实；审计日志写 `new_character` + `character_update` 两笔，回滚时先撤更新再删角色，保持可回溯。
- **细纲生成从“一次塞全本”改为分块**：每 12 章一次调用，注入核心概念/世界观/人物/伏笔/风格笔记；只接受请求章号区间，返回 `missing_chapters`，避免长文截断和乱扩写。
- **批量写作增加硬门控**：后端只允许“已有细纲且正文为空”的章节进入批量写作；已有正文绝不覆盖，缺细纲时明确指路“大纲 → 生成细纲 → 导入笔耕”。
- **仪表盘新增创作流水线**：萌芽定盘/人物档案/世界观/大纲/章节细纲/批量写作/审校发布 7 个阶段的 readiness 与下一步动作，解决“不知道该点哪里”的问题。
- **任何路径保存正典都触发事实提取**：单章保存、批量保存、级联单章保存、级联全部保存统一走同一前端辅助逻辑，避免批量/级联写档后档案落后于正文。
- **写作上下文相关性优先**：500 万字级长篇不再只取“前 20 个角色/前 15 个地点”，先纳入本章细纲、所属脉络、相邻章节中实际提到的实体，再按档案顺序补足；组织档案也纳入写作上下文与记忆检索。

## 遗留事项与待验证假设

- 细纲全本生成按弧顺序串行分块，章数多时耗时较长；当前没有流式进度/取消。建议后续给 `detail_generate` 增加任务进度事件或前端轮询进度。
- 事实提取仍按“保存即自动写档案”执行；重复保存会因同名跳过新实体，但属性更新会重复记录操作日志。后续可增加“与上次提取结果 diff 后仅记录真实变化”。
- kimi-k3 的 thinking 预算（2048）实际可能略超；本次用提高 `max_tokens` 兜底，更省的方案是把 extractor/outliner 绑定到无思考或低思考模型。
- 仪表盘阶段为“可见门禁 + 批量写作硬门控”，未强制禁止用户在萌芽未完成时手动写稿；这与“AI 无权跳步、作者有权自由创作”的定位一致。
