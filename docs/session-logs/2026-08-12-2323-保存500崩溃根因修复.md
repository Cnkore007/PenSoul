# 会话日志:保存 500 崩溃根因修复(LLM 响应防御解析 + 全局 panic 兜底)

- 时间:2026-08-12 23:23
- 类型:线上问题修复

## 任务目标

用户手动测试时遇到「保存失败: HTTP 500」,且发现后端进程消失(3001 无监听)。定位并修复崩溃根因,确保服务稳定。

## 根因分析

1. **现象**:前端「保存」报 500(vite 代理在后端不可达时返回 500);后端进程实际已 panic 退出(axum 0.7 默认对 handler panic 不拦截,panic 会传播到 serve 导致整个进程退出)。
2. **直接根因(两处 panic)**:
   - `pensoul-infra/src/llm/client.rs` `try_complete()`:`json["choices"][0]["message"]["content"]` —— 对 `Value::Null` 做 `[0]` 索引会 panic。部分模型/网关 200 响应无 choices 或结构不同(如错误包装、思考模型流式响应)即触发。
   - 同函数:`&text[..500]` 字节切片 —— 中文错误响应按 500 字节切分极易落在 UTF-8 多字节字符中间,直接 panic。
3. **时间线推断**:用户在配置 LLM 后测试生成/审校时,某个 LLM 响应触发 panic → 进程崩溃 → 之后的保存请求经 vite 代理 → 500。

## 修复方案

- `client.rs`:提取 `parse_content()` 纯函数,全程 `.get()/and_then()` 防御取值,结构异常返回空串不 panic;错误信息改为按字符截断(`chars().take(500)`);新增 2 个回归测试(正常解析 / 缺失 choices 不 panic)。
- `api.rs`:新增全局 panic 兜底 —— `tower_http::catch_panic::CatchPanicLayer::custom(handle_panic)`,任何 handler panic 返回 500 JSON 并打印日志,进程不再退出(最后一层防线)。
- 依赖:`pensoul-app/Cargo.toml` 的 tower-http 增加 `catch-panic` feature(axum 0.7 无内置 CatchPanicLayer;tower 0.5 已移除 HandleErrorLayer,故用 tower-http 自带 custom 处理器)。

## 改动文件清单

- `crates/pensoul-infra/src/llm/client.rs`:防御式 parse_content + 字符截断 + 2 回归测试。
- `crates/pensoul-app/src/api.rs`:handle_panic + CatchPanicLayer::custom 挂载。
- `crates/pensoul-app/Cargo.toml`:tower-http features 加 "catch-panic"。

## 验证结果

- `cargo test` 全仓通过(pensoul-infra 21 项含新增 parse_content 回归;pensoul-app 16 单元 + 22 集成)。
- 后端重启(加载最终代码),冒烟:techniques/open/save 全 HTTP 200;审校本地模式可用。
- 已用 curl 完整复现保存路径(打开项目→保存风格笔记→保存章节→读取),全部正常;冒烟写入的测试内容已恢复为原值。

## 遗留事项与待验证假设

- 崩溃触发点(哪个 LLM 响应结构异常)未拿到原始报文(旧日志丢失);若再次出现,panic 会被捕获并打印到 /tmp/pensoul-server.log,届时按堆栈精确定位。
- 建议用户重新测试:若再遇 500,后端不再崩溃,日志会有 `handler panic 已捕获` 及消息。

## 可复用经验

- axum 0.7 对 handler panic 默认不兜底,进程会崩;生产应挂 CatchPanicLayer(tower-http,需要 catch-panic feature)。
- `serde_json::Value` 的 `json["key"][0]` 对缺失/空值会 panic,解析外部响应必须全程防御取值。
- 中文文本截断必须按字符(`chars().take(n)`),不能用字节切片 `&s[..n]`。
- vite 代理在后端不可达时返回 500,会掩盖真实原因;排查前端 500 先查后端进程是否存活。
