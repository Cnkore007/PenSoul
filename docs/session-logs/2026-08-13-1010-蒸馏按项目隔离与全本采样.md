- 前置：承接 09:30 的 LLM 解析修复（`parse_llm_json`），本次实测中又发现并修复两个稳定性问题

## 用户决策落地

### 决策 1：按项目隔离（作品级）

- 蒸馏文件路径从全局 `data/_config/` 改为 `data/projects/<project_id>/_config/`：
  `distill-corpus.json` / `distill-corpus/` / `style-recipe.json` 全部作品级
- `load_style_recipe` 签名增加 `project_id` 参数；写作（writing.rs）、审校（review.rs）、成本报告（archive.rs）三处消费点同步适配
- 新增 `current_project(&AppState)` 辅助：从当前打开的 ontology 取 project_id，未打开项目时报 400
- **数据迁移**：既有全局语料（《雪中悍刀行》12000 字样本 + 配方）已迁移到当前项目目录，用户资产保留

### 决策 2：阅读完全本后再采样

- `add_corpus` 改为**保存全本**（不再截取 12000 字样本）；`chars` 记录全书字数；响应带 `full_text: true`
- 新增 `sample_across_book(text, budget)`：全书按字符等分 6 区段，每段取约 budget/6 字并标注【开篇】/【中段】/【结尾】，覆盖全书调性；全书不超过预算时直接返回全文
- `analyze` 对每本书调用全本多点采样（预算 60k 字符）后再拼入请求；采样点定位信息随语料一并发给 LLM

## 实测中顺带修复的稳定性问题（蒸馏复测驱动）

1. **thinking 门控 bug**：`build_llm_request` 旧代码无条件携带 `thinking_budget`，client 侧发 `thinking: enabled`——glm-5.2 配置 `thinking_mode=None` 却被强制思考，思考时长短不定，偶发吃光 max_tokens 把 JSON 输出截断成残缺内容（蒸馏/事实提取等结构化功能偶发解析失败的真凶之一）。修复：`ThinkingMode::None` 时不发 thinking。
2. **max_tokens 4000 → 8000**：蒸馏 JSON 体积大（7 维度+基因+禁用清单），给足输出空间防截断。
3. **蒸馏解析失败自动重试 1 次**：GLM 偶发输出主体损坏的 JSON（非包装格式问题，parse_llm_json 无法修复），重试一次显著降低失败率；首次失败打印诊断日志。
4. **parse_llm_json 候选 2 加强**：剥围栏逻辑从 `trim_end_matches("```")`（尾部残留换行时剥不净）改为直接定位 `{`..`}` 主体截取，更健壮。
