# PenSoul 2.0 — 第一性原理重新设计

## 设计哲学

### 从第一性原理出发

**核心洞察：** 创作不是生产，而是生成。生产追求标准化，生成追求涌现性。PenSoul 2.0 的设计目标是：在约束边界内最大化创作的涌现性，同时最小化不一致风险。

**三个根本转变：**

1. **从"流程控制"到"约束边界"**
   - 流程控制是线性的、刚性的
   - 约束边界是非线性的、弹性的
   - 引擎定义"不能做什么"，而非"必须按什么顺序做"

2. **从"记忆存储"到"信息检索"**
   - 存储是静态的、被动的
   - 检索是动态的、主动的
   - 系统应该预测用户需要什么信息，而非被动等待查询

3. **从"事后检测"到"事前预防"**
   - 检测是亡羊补牢
   - 预防是未雨绸缪
   - 在修改时预测影响，在创作时检查一致性

## 核心架构重设计

### 1. 实体图谱引擎（Entity Graph Engine）

**取代：** CDA影响图 + 四层记忆

**本质：** 一个动态的、双向的知识图谱，存储小说中所有实体及其关系

```
┌─────────────────────────────────────────────────────────┐
│                    Entity Graph                          │
├─────────────────────────────────────────────────────────┤
│  Entities                                               │
│  ├── Character (角色)                                    │
│  │   ├── Properties (属性: 年龄、性格、外貌)              │
│  │   ├── States (状态: 当前位置、情绪、关系)              │
│  │   └── History (历史: 状态变化时间线)                   │
│  ├── Event (事件)                                        │
│  │   ├── Participants (参与者: 角色+场景)                │
│  │   ├── Consequences (后果: 影响的实体)                  │
│  │   └── Timeline (时间线: 发生顺序)                     │
│  ├── Setting (设定)                                      │
│  │   ├── Rules (规则: 世界观规则)                        │
│  │   └── Constraints (约束: 不可违反的设定)              │
│  └── Foreshadow (伏笔)                                  │
│      ├── Setup (铺垫: 哪些章节埋下)                      │
│      ├── Payoff (回收: 哪些章节回收)                     │
│      └── Status (状态: 待回收/已回收/废弃)               │
│                                                          │
│  Relations (关系)                                        │
│  ├── Character-Character (角色关系)                      │
│  ├── Character-Event (角色参与事件)                      │
│  ├── Event-Event (事件因果)                              │
│  ├── Setting-Character (设定约束角色)                    │
│  └── Foreshadow-Event (伏笔与事件)                      │
└─────────────────────────────────────────────────────────┘
```

**关键特性：**

1. **双向索引**
   - 正向：角色 → 参与的事件
   - 反向：事件 → 涉及的角色
   - 支持任意实体间的双向查询

2. **时间感知**
   - 每个实体有时间线（状态变化历史）
   - 支持"第X章时角色的状态"查询
   - 自动检测时间线矛盾

3. **影响预测**
   - 修改一个实体时，自动预测可能影响的其他实体
   - 不是"标记受影响"，而是"预测可能的不一致"
   - 在用户修改前给出警告

4. **一致性约束**
   - 用户可以定义硬约束（如"角色A不能死亡"）
   - 引擎在修改时自动检查约束
   - 违反约束时阻止修改或要求确认

### 2. 动态记忆检索（Dynamic Memory Retrieval）

**取代：** 四层记忆系统

**本质：** 根据当前上下文动态选择最相关的信息注入LLM

```
┌─────────────────────────────────────────────────────────┐
│              Memory Retrieval Pipeline                    │
├─────────────────────────────────────────────────────────┤
│                                                          │
│  Input: Current Context (当前章节、光标位置、编辑模式)    │
│                                                          │
│  Step 1: Intent Detection (意图识别)                      │
│    - 用户在写什么？（新内容/修改/审查）                   │
│    - 涉及哪些实体？（角色、场景、事件）                   │
│    - 需要什么上下文？（当前卷/全局/历史）                 │
│                                                          │
│  Step 2: Relevance Scoring (相关性评分)                   │
│    - 实体相关性：与当前内容直接相关的实体                 │
│    - 时间相关性：最近发生的事件                          │
│    - 依赖相关性：被当前内容依赖的设定                    │
│    - 情感相关性：情感连续性相关的片段                    │
│                                                          │
│  Step 3: Budget Allocation (预算分配)                     │
│    - 根据相关性分配token预算                             │
│    - 高相关性实体：完整状态 + 最近历史                   │
│    - 中相关性实体：摘要状态                              │
│    - 低相关性实体：仅提及                                │
│                                                          │
│  Step 4: Context Assembly (上下文组装)                    │
│    - 按重要性排序                                        │
│    - 去重和压缩                                          │
│    - 格式化为LLM可读格式                                │
│                                                          │
│  Output: Optimized Context (优化后的上下文)               │
│                                                          │
└─────────────────────────────────────────────────────────┘
```

**关键特性：**

1. **意图感知**
   - 识别用户当前的创作意图
   - 根据意图调整记忆检索策略
   - 写新内容 vs 修改旧内容 vs 审查一致性

2. **实体追踪**
   - 跟踪当前内容涉及的实体
   - 自动检索相关实体的完整状态
   - 支持"这个角色现在在哪？"的快速查询

3. **情感连续**
   - 维护情感时间线
   - 检测情感跳跃
   - 在上下文中注入情感提示

4. **预算优化**
   - 根据token预算动态调整信息密度
   - 优先保留高价值信息
   - 自动压缩低价值信息

### 3. 约束边界引擎（Constraint Boundary Engine）

**取代：** 确定性流程引擎

**本质：** 定义创作的边界，而非规定创作的流程

```
┌─────────────────────────────────────────────────────────┐
│              Constraint Boundary Engine                   │
├─────────────────────────────────────────────────────────┤
│                                                          │
│  Constraint Types (约束类型)                              │
│  ├── Hard Constraints (硬约束) - 必须满足                │
│  │   ├── Entity Consistency (实体一致性)                 │
│  │   ├── Timeline Order (时间顺序)                       │
│  │   ├── Setting Rules (设定规则)                        │
│  │   └── User-Defined (用户定义)                         │
│  │                                                       │
│  ├── Soft Constraints (软约束) - 建议满足                │
│  │   ├── Style Consistency (风格一致性)                  │
│  │   ├── Pacing Rhythm (节奏韵律)                        │
│  │   └── Foreshadow Balance (伏笔平衡)                  │
│  │                                                       │
│  └── Flexibility Zones (弹性区域) - 允许违反             │
│      ├── Creative Deviation (创作偏离)                   │
│      ├── Style Experiment (风格实验)                     │
│      └── Plot Twist (情节转折)                           │
│                                                          │
│  Boundary Evaluation (边界评估)                           │
│  ├── Pre-Edit Check (修改前检查)                         │
│  │   - 扫描修改内容                                      │
│  │   - 预测可能违反的约束                                │
│  │   - 给出警告或阻止                                    │
│  │                                                       │
│  ├── Post-Edit Validation (修改后验证)                   │
│  │   - 验证修改后的状态                                  │
│  │   - 更新受影响的约束                                  │
│  │   - 标记需要用户确认的变更                            │
│  │                                                       │
│  └── Periodic Audit (定期审计)                           │
│      - 定期扫描全文                                      │
│      - 检测累积的不一致                                  │
│      - 生成审计报告                                      │
│                                                          │
└─────────────────────────────────────────────────────────┘
```

**关键特性：**

1. **约束定义**
   - 用户可以定义全局约束（如"主角不能死亡"）
   - 系统自动推导隐含约束（如"角色A在第5章死了，就不能在第10章出现"）
   - 支持约束分组和优先级

2. **弹性区域**
   - 允许用户标记某些区域为"创作自由区"
   - 在这些区域内，软约束不生效
   - 支持实验性写作

3. **实时检查**
   - 修改时实时检查约束
   - 不是"阻止修改"，而是"提醒风险"
   - 用户可以选择忽略警告

4. **约束传播**
   - 修改一个约束可能影响其他约束
   - 自动检测约束冲突
   - 建议解决方案

### 4. 智能工作流引擎（Intelligent Workflow Engine）

**取代：** 线性流水线

**本质：** 根据上下文和用户行为动态调整工作流

```
┌─────────────────────────────────────────────────────────┐
│           Intelligent Workflow Engine                     │
├─────────────────────────────────────────────────────────┤
│                                                          │
│  Workflow Patterns (工作流模式)                           │
│  ├── Linear Pipeline (线性流水线)                        │
│  │   - 传统的策划→写作→审查→回灌                       │
│  │   - 适用于标准化创作                                  │
│  │                                                       │
│  ├── Iterative Loop (迭代循环)                           │
│  │   - 写作→审查→修改→再审查                           │
│  │   - 适用于高质量要求                                  │
│  │                                                       │
│  ├── Parallel Tracks (并行轨道)                          │
│  │   - 多个章节同时写作                                  │
│  │   - 适用于多线叙事                                    │
│  │                                                       │
│  └── Adaptive Flow (自适应流)                            │
│      - 根据用户行为动态调整                              │
│      - 智能跳过已完成的步骤                              │
│      - 自动插入缺失的步骤                                │
│                                                          │
│  Stage Adapters (阶段适配器)                              │
│  ├── Planning Adapter (策划适配器)                       │
│  │   - 检测是否需要策划                                  │
│  │   - 自动提供相关参考                                  │
│  │                                                       │
│  ├── Writing Adapter (写作适配器)                        │
│  │   - 根据章节类型调整记忆检索                          │
│  │   - 自动注入风格提示                                  │
│  │                                                       │
│  ├── Review Adapter (审查适配器)                         │
│  │   - 根据修改幅度调整审查深度                          │
│  │   - 智能选择审查重点                                  │
│  │                                                       │
│  └── Integration Adapter (集成适配器)                    │
│      - 自动更新实体图谱                                  │
│      - 智能选择需要验证的变更                            │
│                                                          │
│  User Learning (用户学习)                                 │
│  - 学习用户的创作习惯                                    │
│  - 预测用户的下一步操作                                  │
│  - 自动调整工作流                                        │
│                                                          │
└─────────────────────────────────────────────────────────┘
```

**关键特性：**

1. **模式选择**
   - 用户可以选择工作流模式
   - 系统根据章节类型推荐模式
   - 支持混合模式

2. **智能跳过**
   - 检测已完成的步骤
   - 自动跳过不需要的审查
   - 减少重复工作

3. **自动插入**
   - 检测缺失的步骤
   - 自动插入必要的策划
   - 防止质量下降

4. **用户学习**
   - 记录用户的操作模式
   - 预测用户的下一步
   - 自动调整工作流

   - 添加智能跳过
   - 支持并行模式

   - 实现可视化图谱
   - 添加交互功能

3. **约束管理界面**

### Phase 3: 高级功能（3-4个月）

   - 实现用户学习
   - 添加预测功能

   - 实现插件系统
   - 添加导入导出
   - 实现云同步

## 总结

PenSoul 2.0 的核心变化：

1. **从流程控制到约束边界** - 更灵活，更符合创作本质
2. **从记忆存储到信息检索** - 更智能，更高效
3. **从被动检测到主动预防** - 更可靠，更安全
4. **从分离视图到统一画布** - 更直观，更流畅
5. **从单用户到协作支持** - 更强大，更实用

**核心理念：** 约束边界内最大化创作自由，系统主动维护一致性，用户保留最终决定权。
