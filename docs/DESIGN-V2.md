 ## 第一部分：设计哲学与核心理念

 ### 1.1 核心理念：让引擎管流程，让模型管创作

 这个理念直接来自视频中 Harness 引擎的设计哲学，我们将其移植到小说创作领域。

 **问题本质**：当 AI 写小说时，创作流程应该由谁来主导？

 主流做法是把写作流程写成提示词，建议 AI 按步骤来。但建议终究只是建议——AI 会偷懒，会跳步，会跳过一致性检查，会忘记埋设的伏笔。我们的产品走了另一条路：用一个确定性的引擎来硬性驱动创作流程，AI 只负责在每个步骤里把活干好。

 | 维度 | 主流做法 | PenSoul 做法 |
 |------|---------|-------------|
 | 流程控制 | 写在提示词里（建议） | 写进引擎的确定性逻辑（约束） |
 | AI 行为 | AI 自觉遵守，可跳步 | 引擎硬性驱动，不可绕过 |
 | 质量保障 | 可选步骤 | 必经之路（门控放行） |
 | 工作流 | 写死在代码里 | 声明式配置，零代码可换 |
 | 比喻 | 纸条递给司机 | 路上装红绿灯 |

 ### 1.2 设计哲学五原则

 **原则一：硬驱动**
 控制权归引擎，不归模型。创作流程的每一步——大纲生成、章节写作、一致性审查、伏笔检查、文风校准——都是引擎强制执行的关卡，AI 无权跳过。不是不信任 AI 的能力，而是不信任没有约束的能力。

 **原则二：声明式可插拔**
 增加一套创作工作流，只需建一个配置文件夹。想从玄幻小说流程切换到推理小说流程，一条命令搞定。引擎是通用的，流程是可替换的。

 **原则三：正交矩阵**
 执行者（本地/委托）× 门控（自动/人工/条件）= 6 种组合，覆盖几乎所有创作场景。本机+自动=批量生成；委托+条件=专家审查。

 **原则四：零侵入**
 流程引擎在完全不改动底层 AI 执行内核的前提下挂上去。可以随时拔掉，退回到裸循环。流程引擎的 bug 不会污染核心生成能力。

 **原则五：创意空间最大化**
 本地部署的核心价值是反复迭代的创意空间。改一行提示词、替换一个节点、推倒重跑——零 API 成本。创意经常藏在第十次、第二十次的尝试里。

 ## 第二部分：市场调研与竞品深度分析

 ### 2.1 开源项目深度调研

 #### AI-Novel-Writing-Assistant（2131⭐）— 最成熟的开源长篇小说系统

 **架构**：React + Vite 前端 + Express + Prisma 后端 + LangChain/LangGraph Agent 编排 + Qdrant 向量数据库

 **可借鉴的核心设计**：
 - **自动导演开书**：从一句灵感自动规划全书方向、角色、世界观、卷纲、章节
 - **整本生产主链**：章节生成 → AI 审核 → 可修复问题处理 → 质量债务记录 → 角色/事实/伏笔回灌 → 下一章
 - **写法引擎**：写法不再只是提示词，而是可保存、编辑、绑定、试写、复用的长期资产
 - **角色形象演变**：按 25%/50%/75%/100% 覆盖率增量扫描出场章节，生成跨章节一致的形象图
 - **反 AI 规则**：减少正文模板感、解释感和空泛表达

 **局限**：Web 应用，非桌面客户端；无联动修改机制；无跨章节一致性向量

 #### show-me-the-story（399⭐）— 单文件 Go 程序

 **可借鉴的核心设计**：
 - **伏笔系统**：AI 规划伏笔方案，写作时注入活跃伏笔，完成后自动追踪 planted → progressing → resolved/abandoned，超期未回收自动告警
 - **叙事记忆**：每章完成后自动提取大纲未体现的关键叙事细节（角色习惯、具体承诺、道具细节等），跨章节注入写作 prompt
 - **事实核查**：每章写完自动做一致性检查，不通过自动重写
 - **全书优化**：完稿后一键诊断 → 一致性核查 → 生成优化工单 → 逐章自动修订
 - **设定协调**：修改角色/世界观设定后，AI 比对新设定与已写内容，重新生成待写章节大纲

 **局限**：单文件架构，扩展性差；无影响图；无批量联动修改

 #### NovelClaw（352⭐）— 动态记忆感知框架

 **可借鉴的核心设计**：
 - **可编辑记忆库**：memory bank 可直接编辑，跨章节持久化
 - **可检查的运行轨迹**：每次生成都有 progress.log、章节输出、可下载产物
 - **手稿表面**：storyboard、manuscript view、world/character/style panel 作为持续工作面

 ### 2.2 商业产品对比

 | 产品 | 核心优势 | 核心短板 | 我们的差异化 |
 |------|---------|---------|-------------|
 | **Sudowrite** | Story Engine 概念强 | 30K 上下文限制；无跨章记忆；中文差 | 500万字级记忆；中文原生 |
 | **NovelCrafter** | Codex 条目（世界观碎片） | UI 简陋；无自动一致性检查 | 专业 UI；CDA 联动修改 |
 | **NovelAI** | 专用微调模型 | 专注短篇；无长篇结构管理 | 长篇生产主链 |

 ### 2.3 市场空白总结

 1. **无跨章节记忆系统**：现有工具几乎都缺乏 500 万字级别的长期记忆管理
 2. **无联动修改机制**：修改一个章节后，没有工具能自动发现并建议修改受影响的章节
 3. **无确定性流程引擎**：所有工具都依赖 AI 自觉遵守流程，无硬性约束
 4. **无专业级一致性检查**：没有工具能系统性地检测实体状态矛盾、时间线冲突、伏笔管理
 5. **中文支持薄弱**：绝大多数工具以英文为主
 6. **无写法资产系统**：没有工具将"怎么写"沉淀为可复用的长期资产

 ## 第三部分：Harness 引擎 — 小说创作的确定性流程引擎

 这是本设计最核心的创新，直接移植自 Harness 引擎的设计哲学，适配小说创作场景。

 ### 3.1 核心概念映射

 | Harness 概念 | 小说创作映射 | 说明 |
 |-------------|------------|------|
 | 执行内核 (Agent Loop) | LLM 生成器 | 只负责在每一步把文本生成好 |
 | Harness 引擎 | 小说创作流程引擎 | 确定性地驱动整个创作流程 |
 | 阶段 (Stage) | 创作阶段 | 大纲/写作/审查/润色/回灌等 |
 | 阶段状态机 (Stage Machine) | 创作调度器 | 决定当前跑哪个阶段，完成后去哪 |
 | 门控 (Gate) | 质量关卡 | 自动放行/人工放行/条件放行 |
 | 执行者 (Runner) | 本地/委托 | 同一个 AI 换手册，或外包给专家 |
 | 子智能体 (Sub-agent) | 专项 Agent | 独立审查员、风格分析师等 |
 | 信号与双通道 | 审查结果 | 引擎看结构化信号，用户看文本报告 |
 | 工具白名单 | 能力锁定 | 写作阶段不能改设定，审查阶段不能改正文 |
 | 确认方向 (滚动备忘录) | 创作方向备忘 | 规划确认后，后续每个阶段都注入 |

 ### 3.2 小说创作阶段状态机

 ```
 ┌─────────────────────────────────────────────────────────┐
 │                  小说创作 Harness                         │
 │                                                           │
 │  ┌──────┐   ┌──────┐   ┌──────┐   ┌──────┐   ┌──────┐  │
 │  │ 开书  │──▶│ 规划  │──▶│ 写作  │──▶│ 审查  │──▶│ 润色  │  │
 │  │ 定盘  │   │ 大纲  │   │ 章节  │   │ 一致性 │   │ 文风  │  │
 │  └──────┘   └──────┘   └──────┘   └──────┘   └──────┘  │
 │     │           │           │           │           │      │
 │  [人工放行]  [人工放行]  [自动放行]  [条件放行]  [条件放行]  │
 │                                    │           │          │
 │                               ┌────┴────┐  ┌───┴────┐    │
 │                               │ 不通过   │  │ 不通过  │    │
 │                               │ → 回写作 │  │ → 回审查│    │
 │                               └─────────┘  └────────┘    │
 │                                    │                      │
 │                               ┌────┴────┐                │
 │                               │ 通过    │                │
 │                               │ → 回灌  │                │
 │                               └────┬────┘                │
 │                                    │                      │
 │                               ┌────▼────┐                │
 │                               │ 状态回灌 │                │
 │                               │ → 下一章 │                │
 │                               └─────────┘                │
 └─────────────────────────────────────────────────────────┘
 ```

 ### 3.3 阶段定义（声明式配置）

 每个阶段是一张"任务卡"，包含四要素：

 ```yaml
 # 阶段配置示例：章节写作
 stage:
   name: chapter_writing
   display_name: "章节写作"

   # 工作手册：这一步的目标和方法
   manual: |
     根据章节大纲、角色状态、活跃伏笔和前文上下文，
     生成本章正文。严格遵守世界观设定和角色行为模式。

   # 工具白名单：这一步能用哪些工具
   tools:
     allowed:
       - read_chapter_outline    # 读取章节大纲
       - read_character_state    # 读取角色状态
       - read_active_foreshadows # 读取活跃伏笔
       - read_world_settings     # 读取世界观设定
       - generate_prose          # 生成正文
     denied:
       - modify_settings         # 禁止修改设定
       - modify_outline          # 禁止修改大纲
       - delete_chapter          # 禁止删除章节

   # 门控：完成后怎么走
   gate:
     type: auto  # 写完自动进入审查

   # 下一站
   next: chapter_review
 ```

 ```yaml
 # 阶段配置示例：一致性审查
 stage:
   name: chapter_review
   display_name: "一致性审查"

   manual: |
     对本章进行一致性检查：
     1. 实体状态是否与前文矛盾
     2. 时间线是否连续
     3. 角色行为是否符合人格设定
     4. 伏笔是否正确推进
     5. 世界观设定是否被违反

   tools:
     allowed:
       - read_chapter           # 读取章节
       - read_character_state   # 读取角色状态
       - read_consistency_vector # 读取一致性向量
       - run_consistency_check  # 执行一致性检查
     denied:
       - generate_prose         # 审查阶段不能改正文
       - modify_settings        # 审查阶段不能改设定

   gate:
     type: conditional  # 根据审查结果决定放行
     condition: consistency_score >= 80
     on_fail: chapter_writing  # 不通过则回写作

   next: chapter_polish
 ```

 ### 3.4 门控三模式

 | 模式 | 行为 | 适用场景 | 比喻 |
 |------|------|---------|------|
 | **自动放行** | 完成后立即进下一站 | 状态回灌、摘要生成 | 高速公路 ETC |
 | **人工放行** | 必须等用户确认 | 开书定盘、大纲确认 | 收费站窗口 |
 | **条件放行** | 根据检查结果决定 | 一致性审查、风格校准 | 检查站 |

 ### 3.5 执行者矩阵

 执行者有两种模式，与门控正交组合：

 | | 自动放行 | 人工放行 | 条件放行 |
 |---|---------|---------|---------|
 | **本机执行** | 批量生成（AI 连续写多章） | 交互式写作（AI 写一段等确认） | 自动审查（AI 自查） |
 | **委托执行** | 自动化流水线 | 专家会诊 | 独立审查（最常用） |

 **委托执行的关键价值**：审查不应该让写正文的 AI 自己审查自己（等于学生自己给自己判卷）。委托一个独立的审查 Agent，用更强的模型，专注做质量把关。

 ### 3.6 信号与双通道

 当审查 Agent 完成检查后，产出走两条路：

 ```
 审查 Agent 产出
       │
       ├──▶ 信号通道（仅引擎可见）
       │    结构化 JSON：{ pass: true/false, score: 87, issues: [...] }
       │    引擎据此决定放行或拦截
       │
       └──▶ 文本通道（仅用户可见）
            人类语言报告："本章一致性评分 87，发现 2 处潜在矛盾..."
            用户看到干净的报告，看不到技术格式
 ```

 ### 3.7 滚动备忘录（确认方向）

 规划阶段确认的大纲方向，存为一张滚动备忘录。在后续每个阶段、每次 AI 开工前都注入进去。保证写到第 50 章时，AI 还记得第 1 章定下的核心冲突和角色弧线。

 ## 第四部分：Agent 本体论与四层世界模型

 ### 4.1 小说本体论框架

 每部小说维护一个四层本体，层与层之间通过引用关系连接：

 ```
 ┌─────────────────────────────────────────────────────────┐
 │              小说本体 (Novel Ontology)                    │
 ├─────────────────────────────────────────────────────────┤
 │                                                           │
 │  Layer 4: 审美层 (Aesthetic Layer)                         │
 │    ├─ 文风指纹 (Style Fingerprint)                         │
 │    ├─ 叙事节奏模型 (Pacing Model)                          │
 │    └─ 反 AI 规则库 (Anti-AI Rules)                         │
 │                                                           │
 │  Layer 3: 叙事层 (Narrative Layer)                         │
 │    ├─ 情节图谱 (Plot Graph)                                │
 │    ├─ 伏笔追踪器 (Foreshadow Tracker)                      │
 │    ├─ 冲突矩阵 (Conflict Matrix)                           │
 │    └─ 情感弧线 (Emotional Arc)                             │
 │                                                           │
 │  Layer 2: 角色层 (Character Layer)                         │
 │    ├─ 角色状态机 (Character State Machine)                  │
 │    ├─ 关系拓扑图 (Relationship Topology)                    │
 │    ├─ 角色成长曲线 (Character Growth Curve)                │
 │    ├─ 对话风格库 (Dialogue Style Library)                  │
 │    └─ 角色知识库 (Character Knowledge Base)                │
 │                                                           │
 │  Layer 1: 世界层 (World Layer)                             │
 │    ├─ 空间模型 (Spatial Model)                             │
 │    ├─ 时间线 (Timeline)                                    │
 │    ├─ 设定规则库 (Setting Rules DB)                        │
 │    ├─ 术语词典 (Terminology Glossary)                      │
 │    └─ 物品/道具图谱 (Item/Prop Graph)                      │
 │                                                           │
 └─────────────────────────────────────────────────────────┘
 ```

 **交互规则**：
 - 下层为上层提供"事实基础"——角色行为必须符合世界规则
 - 上层对下层施加"约束"——情节需要角色来推动
 - 同层之间通过"引用"连接——叙事层的伏笔引用角色层的角色和世界层的物品

 ### 4.2 角色状态机

 每个角色维护一个形式化的状态机，记录所有状态转换：

 ```typescript
 interface CharacterStateMachine {
   // 基础属性（不可变）
   id: CharacterID;
   name: string;
   corePersonality: PersonalityVector; // 核心人格，基本不变

   // 可变状态
   currentMood: Emotion;
   currentLocation: LocationID;
   currentKnowledge: KnowledgeSet; // 角色"知道什么"
   currentRelationships: RelationshipMap;

   // 状态转换历史
   stateHistory: StateTransition[];

   // 状态转换规则：什么事件触发什么变化
   transitionRules: TransitionRule[];
 }

 interface StateTransition {
   from: CharacterState;
   to: CharacterState;
   trigger: EventID;       // 触发事件
   chapterId: ChapterID;   // 发生在哪章
   timestamp: StoryTime;   // 故事内时间
   causality: string;      // 因果链描述
 }
 ```

 ### 4.3 角色知识库（防信息穿越）

 每个角色维护独立的知识库，追踪"这个角色知道什么"和"不知道什么"。防止角色 A 在第 5 章不应该知道的信息出现在第 3 章的对话中。

 ```typescript
 interface CharacterKnowledgeBase {
   characterId: CharacterID;

   // 已知信息（按获取时间排序）
   knownFacts: KnowledgeItem[];

   // 信息来源追踪
   knowledgeSources: Map<FactID, {
     source: 'observed' | 'told' | 'inferred' | 'remembered';
     obtainedAt: ChapterID;
     obtainedFrom?: CharacterID; // 谁告诉他的
     reliability: number;        // 信息可靠度 0-1
   }>;

   // 信息衰减：久远的细节可能被遗忘
   decayModel: DecayFunction;
 }
 ```

 ## 第五部分：CDA 一致性驱动架构

 ### 5.1 影响传播模型

 当用户修改第 N 章某段落时：

 ```
 用户修改第 N 章
       │
       ▼
 ┌─────────────────────────┐
 │  变更检测器               │
 │  • 实体提取与比对          │
 │  • 属性变化量化            │
 │  • 时间线偏移检测           │
 └──────────┬──────────────┘
            │
            ▼
 ┌─────────────────────────────┐
 │  影响图遍历                   │
 │                               │
 │  直接影响：                    │
 │    → 同章节其他段落            │
 │    → 紧接的前后章节            │
 │    → 本章角色的当前状态        │
 │                               │
 │  间接影响：                    │
 │    → 世界观设定文档            │
 │    → 伏笔/回收记录            │
 │    → 角色关系图               │
 │    → 时间线                   │
 │    → 远端章节（通过引用链传播） │
 │                               │
 │  级联影响：                    │
 ```

 ## 第六部分：长期记忆与上下文管理

 > **核心原则：效果优先，不计成本。**
 > 本系统的记忆策略不设 token 预算上限。能注入多少上下文就注入多少，
 > 能检索多少相关信息就检索多少。写出一致性好、质量高的小说是唯一目标，
 > token 开销不是考量因素。宁可多花 token 也不牺牲一个细节。

 500 万字约等于 2000-2500 个章节。采用四层记忆架构：

 ### 6.1 记忆层次模型

 ```
 ┌──────────────────────────────────────────────────┐
 │           热记忆 (Hot Memory) — 无上限             │
 │  当前正在编辑的章节 ± 前后 5 章                      │
 │  完整文本，直接注入 LLM 上下文                        │
 │  无 token 上限，能放多少放多少                        │
 ├──────────────────────────────────────────────────┤
 │          温记忆 (Warm Memory) — 全量注入           │
 │  当前卷/弧的全部摘要 + 所有角色状态 + 全部活跃伏笔       │
 │  结构化 JSON，全量注入                               │
 │  不做裁剪，不做采样                                   │
 ├──────────────────────────────────────────────────┤
 │          冷记忆 (Cold Memory) — 全量检索           │
 │  全书级别：世界观设定、完整时间线、所有角色档案            │
 │  向量数据库索引，Top-K 设为最大值                     │
 │  召回所有语义相关的结果                                │
 ├──────────────────────────────────────────────────┤
 │         冰记忆 (Archive Memory) — 按需全量         │
 │  已完成章节的原始文本                                 │
 │  精确匹配检索，命中则全量加载                          │
 │  不做截断                                           │
 └──────────────────────────────────────────────────┘
 ```

 ### 6.2 记忆更新管道

 每完成一个章节，自动触发：

 1. 提取新叙事要素（实体、事件、关系变化）
 2. 更新角色状态机
 3. 更新时间线
 4. 更新伏笔状态（planted → progressing → resolved）
 5. 重新生成章节摘要
 6. 更新一致性向量
 7. 更新影响图
 8. 更新叙事记忆（大纲未体现的关键细节）

 ### 6.3 叙事记忆（来自 show-me-the-story 的启发）

 大纲只记录骨架，但小说的灵魂藏在细节里。每章完成后，系统自动提取：
 - 角色的小习惯和口头禅
 - 具体的承诺和约定
 - 道具的细节描述
 - 环境的感官描写
 - 未被大纲覆盖的情节暗线

 这些细节存入叙事记忆，后续章节写作时按相关性检索注入，弥补大纲摘要的信息缺口。

 ## 第八部分：核心功能设计

 ### 8.1 创作五阶段流程

 #### 阶段一：开书定盘

 - 输入：一句灵感/梗概/参考作品
 - AI 自动整理项目设定、对齐书级 framing
 - 生成多套整本方向和对应标题组
 - 用户选择/调整后确认 → 滚动备忘录创建

 #### 阶段二：规划

 - Plot Architect Agent 生成多层大纲
 - 伏笔地图：埋设计划和回收时间表
 - 角色弧线：每个重要角色的成长路径
 - 卷级骨架：节奏板 + 拆章
 - **门控：人工放行**（用户确认大纲后才能进入写作）

 #### 阶段三：写作

 - Scene Writer Agent 按场景逐段生成
 - 自动注入热记忆（前 2 章完整文本）+ 温记忆（角色状态、活跃伏笔）
 - 支持四种模式：自动/交互/续写/对话
 - **门控：自动放行**（写完自动进入审查）

 #### 阶段四：审查（委托执行 + 条件放行）

 - Consistency Auditor（独立 Agent）执行一致性检查
 - 伏笔状态更新
 - 影响图更新
 - 双通道输出：结构化信号给引擎，文本报告给用户
 - **门控：条件放行**（一致性评分 ≥ 80 通过，否则回写作）

 #### 阶段五：润色 + 回灌

 - Style Analyzer 校准文风
 - 反 AI 规则检查
 - 状态回灌：更新所有层级的记忆
 - 进入下一章

 ### 8.2 写法资产系统（来自 AI-Novel-Writing-Assistant）

 写法不再只是提示词里的一段说明，而是可保存、编辑、绑定、试写、复用的长期资产：

 - **写法提取**：从用户已有文本中提取风格特征 + 原文样本
 - **特征池**：句长分布、词汇丰富度、修辞频率、节奏模型等
 - **反 AI 规则**：禁用 AI 高频套话、模板化表达、空泛描述
 - **写法绑定**：每个项目/章节可以绑定不同的写法资产
 - **试写对比**：同一段内容用不同写法资产生成，用户对比选择

 ### 8.3 伏笔全生命周期管理（来自 show-me-the-story）

 ```
 规划阶段：AI 建议 3-8 条伏笔（含埋设章节和预计回收章节）
 ```

 ### 8.4 设定协调（来自 show-me-the-story）

 已经写了若干章之后修改了角色/世界观等关键设定？保存时系统提示进行"设定协调"：

 1. AI 比对新设定与已写内容
 2. 输出兼容版设定
 3. 基于新设定重新生成尚未写作章节的大纲
 4. 标注已写章节中与新设定矛盾的内容

 ### 8.5 全书优化流水线

 全部章节完成后的一键优化：

 1. AI 通读设定与正文
 2. 输出诊断报告 + 一致性报告 + 可执行工单

## 第十一部分：并发控制架构

> **设计原则**：效果优先。并发控制的目标是保证创作流程不中断，而非节省资源。

### 11.1 问题场景

用户手动编辑第 10 章时，AI 后台正在生成第 11 章。两者可能同时修改角色状态、伏笔状态等共享数据。

### 11.2 操作队列 + 乐观锁方案

```
┌─────────────────────────────────────────────────┐
│                  操作队列 (Operation Queue)        │
│                                                   │
│  用户编辑 ──▶ [入队] ──▶ [获取章节锁] ──▶ [应用]    │
│  AI 生成  ──▶ [入队] ──▶ [获取章节锁] ──▶ [写入]    │
│  自动回灌 ──▶ [入队] ──▶ [获取共享锁] ──▶ [更新]    │
│                                                   │
│  所有操作排队执行，同一时刻只有一个操作修改同一章节       │
└─────────────────────────────────────────────────┘
```

**锁策略**：
- **章节级锁**：修改某一章时锁定该章，不锁全书
- **乐观锁**：基于版本号检测冲突。操作提交时检查版本号，不匹配则提示用户合并
- **共享锁**：只读操作（如一致性检查）可以并发执行
- **排他锁**：写入操作（如 AI 生成、用户编辑）独占执行

### 11.3 冲突合并策略

当用户编辑和 AI 生成同时修改同一章节时：
1. 检测冲突区域（基于文本 diff）
2. 如果修改区域不重叠，自动合并
3. 如果修改区域重叠，展示双栏 diff 让用户选择
4. 保留完整的修改历史，支持任意版本回滚

## 第十二部分：Agent 双通道通信协议

> **设计原则**：效果优先。双通道确保引擎控制信号和用户可见报告互不干扰，提升创作质量。

### 12.1 协议设计

Sub-agent 与主流程之间的通信采用双通道 JSON 协议：

```json
{
  "message_id": "uuid-v4",
  "channel": "signal",
  "from_agent": "consistency_auditor",
  "to_engine": "harness",
  "timestamp": "2026-07-26T15:30:00Z",
  "payload": {
    "signal": {
      "pass": true,
      "score": 87,
      "severity_levels": {
        "critical": 0,
        "warning": 2,
        "info": 5
      },
      "retry": false
    },
    "report": {
      "human_summary": "本章一致性评分 87/100。发现 2 处潜在矛盾和 5 处信息建议。",
      "details": [
        {"type": "warning", "desc": "第3段角色A的情绪与前文矛盾", "chapter": 10, "para": 3},
        {"type": "info", "desc": "建议在第5段补充时间线说明", "chapter": 10, "para": 5}
      ]
    },
    "metadata": {
      "model_used": "gpt-4o",
      "duration_ms": 1200
    }
  }
}
```

### 12.2 双通道隔离原则

- **信号通道**（`channel: "signal"`）：只有引擎读取，格式严格结构化
- **文本通道**（`channel: "report"`）：只有用户可见，纯人类语言
- 两通道打包在同一个消息中，但解析路径完全独立
- 用户永远看不到 `pass: true/false` 这样的技术格式
- 引擎永远不解析报告的自然语言内容

### 12.3 支持的 Agent 类型

| Agent | 职责 | 输出信号 |
|-------|------|----------|
| ConsistencyAuditor | 一致性审查 | pass/fail + score |
| StyleAnalyzer | 文风校准 | pass/fail + style_score |
| ForeshadowTracker | 伏笔追踪 | status_update + alerts |
| DialoguePolisher | 对话打磨 | pass/fail + quality_score |
| PlotArchitect | 大纲规划 | outline_proposal |
| WorldBuilder | 世界观构建 | world_spec |

| report通道路由 | ✅ 通过 | 用户报告正确路由到UI |

## 第十四部分：增量一致性检查

> **设计原则**：效果优先。宁可多检查几遍，也不放过一个矛盾。不计成本，只求质量。

### 14.1 增量检查策略

不做全书一致性检查（太慢），而是基于影响图做增量检查：

```
用户修改第 N 章
      │
      ▼
影响图查询 -> 找到受影响节点列表
      │
      ▼
仅检查受影响节点所在的章节
      │
      ▼
生成差异报告
```

### 14.2 检查范围界定（分层策略）

| 实体类型 | 检查范围 | 原因 |
|---------|---------|------|
| 角色状态 | 增量（仅本章） | 角色变化通常局部影响 |
| 世界观设定 | 全量（所有章节） | 设定变更可能影响任何章节 |
| 时间线 | 相邻章节 | 时间冲突通常局部 |
| 伏笔 | 相邻章节 | 伏笔埋设和回收通常相邻 |
| 事件/剧情 | 增量（仅本章） | 事件变化通常局部 |

### 14.3 增量检查 vs 全量检查

- **增量检查**（默认）：只检查受影响部分，秒级完成
- **全量检查**（可选）：完稿后一键全书扫描，分钟级完成
- **混合模式**：每章完成后增量检查，每卷完成后全量检查

### 14.4 验证数据

| 验证项 | 结果 | 数据 |
|--------|------|------|
| 分层策略 | ✅ 通过 | 角色=增量，设定=全量，伏笔=相邻 |
| 跨章状态对比 | ✅ 通过 | 检测到设定交换率变化（2个违反） |
| 实体状态管理 | ✅ 通过 | 2个实体，8个状态快照 |

## 第十六部分：LLM 模型管理

> **设计原则**：效果优先，不计成本。用户完全掌控模型选择，系统提供智能推荐但不做自动决策。

### 16.1 模型选择模式：用户手动选择

本系统采用**用户手动选择模型**的模式，而非自动路由。理由：
- 创作者对自己的作品有最深的理解，知道什么模型最适合自己的风格
- 不同作者对模型质量的偏好不同（有人喜欢 Claude 的文风，有人喜欢 GPT-4o 的推理）
- 用户可能有自己微调的模型或特定的 API 配置
- 自动路由会剥夺用户的创作自主权

### 16.2 模型配置界面

```
┌─────────────────────────────────────────────────────────┐
│                   模型设置面板                             │
│                                                           │
│  📋 已配置模型：                                          │

│  │ 模型名称     │ 提供商   │ 状态     │ 操作   │          │
│  ├─────────────┼──────────┼──────────┼────────┤          │
│  │ GPT-4o      │ OpenAI   │ ✅ 已连接 │ ⚙️ 🔑  │          │
│  │ Claude 4    │ Anthropic│ ✅ 已连接 │ ⚙️ 🔑  │          │

│  ┌─────────────┬─────────────────────┬──────────┐        │

└─────────────────────────────────────────────────────────┘
```

### 16.3 模型管理功能

**添加模型**：
- 支持 OpenAI、Anthropic、DeepSeek、本地 Ollama 等主流提供商
- 用户填写 API Key 和端点地址
- 系统自动测试连接并显示状态
- 支持自定义模型名称和备注

**模型分配**：
- 用户可以为每个任务类型（大纲、写作、审查等）指定不同的模型
- 同一个模型可以分配给多个任务
- 用户可以随时修改分配方案
- 系统会保存用户的偏好设置

**智能推荐**：
- 在模型选择下拉框旁显示"推荐"标记
- 推荐基于：模型能力评估、用户历史使用效果、任务匹配度
- 推荐仅供参考，用户可以忽略

### 16.4 容灾机制

当用户选择的模型不可用时，系统会：

```
用户选择的模型调用失败
      │
      ▼
弹出提示："模型 xxx 暂时不可用，是否切换到备用模型？"
      │
      ├──▶ [切换] → 使用用户预设的备用模型
      │
      └──▶ [重试] → 等待后重试原模型
      │
      └──▶ [取消] → 用户手动选择其他模型
```

**备用模型设置**：
- 用户可以为每个任务类型设置一个"备用模型"
- 当主模型连续失败 3 次后，自动切换到备用模型
- 切换前会通知用户，并提供"切换回去"的选项

### 16.5 多模型对比功能

对于追求极致效果的用户，支持：

- **多模型生成**：同一章节用 2-3 个模型各生成一遍
- **对比预览**：并排展示不同模型的生成结果
- **选择采纳**：用户选择最佳版本，或组合不同版本的优点
- **效果评估**：记录用户的选择偏好，优化推荐
